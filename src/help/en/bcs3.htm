BCS3

The BCS3 is a self-build computer developed by Eckhard Schiller, whose construction plans were published in 1985 in the magazine Radio Fernsehen Elektronik. This computer is notable for its clever design, which offers acceptable computing performance despite a minimal number of components.

1. Emulated Hardware

  • Depending on the setting, 2, 4, or 5 KByte ROM
  • 1 KByte RAM (3C00h-3FFFh)
  • Cassette recorder connection
  • Optionally a memory expansion with 16 KByte RAM (4000h-7FFFh)

1.1. Screen Output

On the BCS3, the video signal is essentially generated by a cyclically invoked software routine. This routine reads the characters to be output from working memory and drives the hardware in such a way that the desired video signal is produced. JKCEMU visualizes the video signal produced in this way.

1.2. Cassette Recorder Connection

On the output side, the cassette recorder connection is served by the same CTC channel that also supplies the horizontal sync pulses (HSync pulses) for the screen output. For this reason you will (normally) hear a whistling sound when you activate an audio function to output sound. The whistling is the horizontal sync pulses being output at half frequency. Only with the BASIC command SAVE are the tones known for data storage generated. As soon as the BASIC program has been output on the cassette recorder connection, screen output becomes active again, and you will hear the whistling again as well.

Since the HSync pulses can be a nuisance, especially if you want to save the BASIC program to a sound or tape file, the settings offer the option Remove HSync signals from audio output. When this option is enabled, which is the default, the HSync pulses are filtered out and you hear only the actual tone output.

Caution! BASIC-SE 2.4 does not include support for saving to or loading from cassette. The LOAD and SAVE commands jump to address 0800 or 0803 respectively, i.e. outside the ROM area. You can install your own routines for loading and saving there. However, since there is normally no valid program code there by default, the LOAD and SAVE commands result in undefined behavior.

2. Software Contained in ROM

Depending on the setting:
  • BASIC-SE 2.4 (0000h-07FFh) for 27 visible characters per line and a 2.5 MHz clock frequency
  • BASIC-SE 3.1 (0000h-0FFFh) for 29 visible characters per line and a 2.5 MHz clock frequency
  • BASIC-SE 3.1 (0000h-0FFFh) for 40 visible characters per line and a 3.5 MHz clock frequency
    (bug-fixed version (address 018Ah: byte 29h changed to 09h), so that the PLOT command works)
  • S/P-BASIC V3.3 (0000h-0FFFh) for 29 visible characters per line and a 2.5 MHz clock frequency
  • Machine Code Editor (F000h-F3FFh, only in conjunction with BASIC-SE 3.1 for 29 visible characters per line)

2.1. Notes on BASIC-SE 3.1 and S/P-BASIC V3.3

  • At system start, BASIC checks whether memory has already been initialized and, depending on that, performs either a cold start or a warm start. On a warm start, the system cells in working memory are not reinitialized. Consequently, a RESET usually results in a warm start, since memory has already been initialized.

  • On a cold start, you must first enter the number of visible lines (BASIC-SE 3.1: 4 to 29, S/P-BASIC 3.3: 4 to 28) and press ENTER, before you reach the BASIC prompt.

  • The memory area for the BASIC program begins after the video memory, i.e. the more visible lines there are, the further back the BASIC program begins.

    Caution! For example, if you save a BASIC program with the emulator functions while at 8 visible lines and then load it again at 12 lines, you must load the BASIC program to a different address, otherwise you will overwrite the video memory! And that is likely to crash the BCS3! Therefore, save and load BASIC programs as described further below.

  • S/P-BASIC V3.3 is not backward compatible with BASIC-SE 3.1, and that in turn is not backward compatible with version 2.4, i.e. BASIC programs only run with the version they were typed in with. The tokens, and thus the binary format, differ among all three versions.

3. Miscellaneous

3.1. Saving and Loading BASIC Programs

Save BASIC programs using the corresponding function of the emulator (menu File → Save BASIC Program...). Since the BASIC program may need to be loaded back in at a different address depending on the number of visible lines, the load address should not be stored in the file. For this reason, it is best to use memory image files without header data (BIN files).

When loading a BASIC program, you should always proceed in such a way that the dialog with the load options is shown (see load options). JKCEMU determines the load address to be used and writes it into the corresponding field in the load options. For this to happen, however, the dialog must actually be shown. For memory image files without header data, that is always the case.
