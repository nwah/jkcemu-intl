BASIC Compiler

Target Systems

The BASIC compiler can generate program code for various systems. Several systems that are related to each other and on which the same program code can run are grouped together. This group forms a target system. Programs compiled for a particular target system are therefore able to run on all computers that correspond to the specified target system.

The target system must be selected or specified in the compiler options. This tells the compiler what kind of program code is to be generated. The following target systems are supported:
  • AC1-2010, AC1-SCCH with optional color graphics card
  • CP/M-compatible
  • Hübler-Grafik-MC
  • Kramer-MC
  • LLC2 with HIRES graphics
  • KC85/1, KC87, Z9001
  • KC85/1, KC87, Z9001 with KRT graphics
  • KC85/2..5, HC900
  • KC85/4..5 with support for both video memory banks
  • KC85/5 with CAOS >= 4.8
  • SCCH (AC1-2010, AC1-SCCH, LLC2)
  • Z1013
  • Z1013 with support for the 64x16 screen format
  • Z1013 with KRT graphics
  • Z1013 with ZX graphics

At the end of the page you will find a table summarizing the target systems.

Not all BASIC functionality can be implemented on every target system. There are limitations, in particular, for the graphics and CURSOR functionality. For this reason, you will find notes here on the concrete implementations and the associated limitations.

AC1-2010, AC1-SCCH with optional color graphics card

For this target system, program code with color support is generated for an AC1-2010 and AC1-SCCH. Color support means that, for all output to the screen, the color memory is written to in addition to the video refresh memory. However, the compiled program will also run on an AC1 without a color graphics card. Only the POINT function, used to determine the color of a pixel, would return incorrect values in that case.

The AC1 monitor programs do not support colors by default. For this reason, the compiled program must do so itself. To do this, the compiler checks whether the BASIC program contains statements for setting the color. If so, text output to the screen is not performed via the corresponding system function, but instead via its own screen driver included in the compiled program, which also writes to the color memory. This custom screen driver does not support all control codes of the system routine, only the most important ones:

Control codeMeaning
08hCursor left
09hCursor right
0AhCursor down
0BhCursor up
0ChClear screen
0Dh Cursor to the start of the next line

Other control codes, in particular the escape sequences known from the system routine, are not supported.

For cursor positioning, the custom screen driver uses the same system cells as the SCCH monitor programs, namely 1800h/1801h for the cursor address and 1846h for the character under the cursor. This ensures that the cursor does not jump when the program starts and ends.

If the BASIC program contains no statements for setting the color, the compiled program also contains no functions for writing to the color memory. In that case, the graphics functions (simulated full graphics, see further below) only write to the video refresh memory, and the monitor program's system function is used for text output.

In SCREEN 0, full graphics with 128x64 pixels are simulated and can be addressed with the graphics functions. A prerequisite for this is that the character generator contains the corresponding graphics characters in the range 00h to 0Fh. This is the case with the ACC, SCCH and AC1-2010 character sets.

With simulated full graphics, each character position on the screen is divided into four graphics pixels. Since a character is 8x6 screen pixels, a simulated graphics pixel is 4x3 screen pixels in size, i.e., a graphics pixel is not square. As a result, circles drawn on the screen look like ellipses and squares look like rectangles.

The generated program code also runs on an AC1 with monitor program 3.1, provided a 2 KByte video refresh memory is present (64x32 characters) and printer output as well as the JOYST function are not used.

Properties of the target system in detail:
  • A single-character application name is supported, i.e., if the name field contains only one character, a corresponding command frame is generated, and the compiled program can be invoked using that character.
  • In SCREEN 0, full graphics with 128x64 pixels are simulated and can be addressed with the graphics statements.
  • The CURSOR statement has no effect.
  • The PAUSE statement is calibrated to the standard clock frequency of the AC1 (2 MHz).
  • The DATETIME$ function requires a GIDE connected at I/O base address 80h.
  • The JOYST function supports a joystick and, for this purpose, calls the system function at address 0EB4h.
  • A VDIP module is supported at I/O base addresses DCh, FCh and 08h (PIO2), i.e., an attempt is first made to initialize the VDIP module at base address DCh. If that fails, base address FCh is tried next, then 08h.
  • The constant for the target system is: TARGET_AC1
  • This target system is derived from the target system SCCH (AC1-2010, AC1-SCCH, LLC2), i.e., the function IS_TARGET also returns TRUE for TARGET_SCCH.

CP/M-compatible

  • The graphics statements are not available.
  • The CURSOR statement has no effect.
  • The DATETIME$ function is not supported, i.e., it always returns an empty string.
  • The JOYST function always returns 0.
  • Reading the cursor position is not possible, i.e., the POS function always returns -1, and the system variables CRSLIN and CRSPOS always contain the value -1.
  • A VDIP module is supported at I/O base address FCh.
  • The constant for the target system is: TARGET_CPM

Hübler-Grafik-MC

  • The graphics statements access the video refresh memory directly. For this, it must be set to the standard address C000h.
  • CURSOR statement: turning the cursor on only takes effect with the next character output. Turning the cursor off, however, takes effect immediately.
  • The DATETIME$ function is not supported, i.e., it always returns an empty string.
  • The JOYST function always returns 0.
  • Reading the cursor position is not possible, i.e., the POS function always returns -1, and the system variables CRSLIN and CRSPOS always contain the value -1.
  • A VDIP module is supported at I/O base address FCh.
  • The constant for the target system is: TARGET_HUEBLER

Caution! Programs compiled for the Hübler-Grafik-MC will also run on the Hübler/Evert-MC, provided the graphics functionality and the INKEY$ function are not used, and the program is not compiled with the option CTRL-C always aborts the program.

Kramer-MC

  • The graphics statements are not available.
  • The CURSOR statement has no effect.
  • The LOCATE statement is not available.
  • The DATETIME$ function is not supported, i.e., it always returns an empty string.
  • The Kramer-MC monitor program built into JKCEMU only recognizes the key combination CTRL-C for the INKEY$ function.
  • Printer output is performed via the LIST channel (entry address 00ECh). However, the Kramer-MC monitor program included in JKCEMU is configured by default so that the LIST channel, and thus the printer output, appears on the screen.
  • The JOYST function always returns 0.
  • No VDIP module is supported.
  • You must not enable the compiler option Use system stack, since, when a machine code program is started with the command G<address>, the stack pointer has the value 0000 and would therefore run into the video refresh memory. Always compile with the option Separate stack area.
  • The constant for the target system is: TARGET_KRAMER

LLC2 with HIRES graphics

  • A single-character application name is supported, i.e., if the name field contains only one character, a corresponding command frame is generated, and the compiled program can be invoked using that character.
  • SCREEN 0 is a pure text screen, in which the graphics statements cannot be used.
  • The HIRES full graphics extension with 512x256 pixels is available in SCREEN 1, i.e., the graphics statements can be used here. Text output performed with statements other than LABEL goes to SCREEN 0, which, however, is not visible at that moment. In SCREEN 1, the video refresh memory is located at address 8000h and thus occupies a different area than in SCREEN 0.
  • The CURSOR statement has no effect.
  • The DATETIME$ function requires a GIDE connected at I/O base address 80h.
  • The JOYST function supports a joystick and, for this purpose, calls the system function at address 0EB4h.
  • A VDIP module is supported at I/O base addresses DCh, FCh and E4h (PIO2), i.e., an attempt is first made to initialize the VDIP module at base address DCh. If that fails, base address FCh is tried next, then E4h.
  • The constant for the target system is: TARGET_LLC2
  • This target system is derived from the target system SCCH (AC1-2010, AC1-SCCH, LLC2), i.e., the function IS_TARGET also returns TRUE for TARGET_SCCH.

KC85/1, KC87, Z9001

  • In SCREEN 0, full graphics with 80x48 pixels are simulated using block graphics and can be addressed with the graphics statements.
  • If the BASIC program uses the statements BORDER, COLOR, INK or PAPER, program code with color support is generated, i.e., in that case, every pixel-setting graphics statement also writes to the color memory. If, on the other hand, no statements for setting the color are used, program code is generated that does not access the color memory.
  • The DATETIME$ function requires a GIDE connected at I/O base address 50h.
  • A VDIP module is supported at I/O base address DCh.
  • The constant for the target system is: TARGET_Z9001

KC85/1, KC87, Z9001 with KRT graphics

  • SCREEN 0 is a pure text screen. Full graphics are not simulated, i.e., the graphics statements cannot be used here.
  • The KRT full graphics with 320x192 pixels are available in SCREEN 1, i.e., the graphics statements can be used here. Text output, however, is not possible (except with the LABEL statement).
  • Regarding color support, the same applies as for the target system KC85/1, KC87, Z9001, with one exception:
    CLS in SCREEN 1 (graphics mode) always clears the color memory, even if the BASIC program contains no statements for setting the color.
  • Regarding the DATETIME$ function, the same applies as for the target system KC85/1, KC87, Z9001.
  • Regarding VDIP, the same applies as for the target system KC85/1, KC87, Z9001.
  • The constant for the target system is: TARGET_Z9001_KRT
  • This target system is derived from the target system KC85/1, KC87, Z9001, i.e., the function IS_TARGET also returns TRUE for TARGET_Z9001.

KC85/2..5, HC900

This target system generates program code that runs on all Mühlhausen KCs, from the HC900 up to the KC85/5.

Properties of the target system in detail:
  • Keyboard input and screen output are performed via the respective standard channel, i.e., input and output can be redirected in CAOS. This does not, however, apply to the INKEY$ function. This always accesses the keyboard directly, even if keyboard input has been redirected.
  • Printer output is performed on user channel 2.
  • The LOCATE statement refers to the window currently set in CAOS.
  • On the HC900 and the KC85/2, the current window is set smaller than the maximum possible size by default. In that case, the CLS statement does not clear the entire screen. Since this looks unattractive, the compiler checks whether the program contains CLS statements. If so, at program start the size of the window currently set in CAOS is checked and, if necessary, maximized.
  • The CURSOR statement has no effect. CAOS switches the cursor on and off automatically, depending on whether input is currently being waited for or not.
  • The first time the system time is read after the program starts (e.g. by the DATETIME$ function), a source for the system time is searched for and the result is remembered. On subsequent reads of the system time, this same source is then always used, even if it should no longer be delivering valid values. The reverse also applies: if no source for a system time was found at the start, all subsequent queries will also fail to return a system time.
    The search for a source for the system time proceeds as follows:
    1. It is checked whether a D004 or D008 floppy disk expansion is connected.
    2. If so, it is checked whether a floppy disk expansion program (DEP) version 3.0 or higher is running on it. If so, it writes the system time cyclically into the coupling RAM, and the associated I/O addresses on the base unit's side are used as the source for the system time.
    3. If no D004/DEP or D008/DEP pairing was found, the compiled BASIC program checks the memory cells at addresses 000Ch to 000Fh for valid values corresponding to a DOS timestamp.
    4. If a valid DOS timestamp was found, that does not yet mean that a system clock exists and is running that updates this timestamp. For this reason, an additional check is made to see whether the time (memory cells 000Eh/000Fh) has the value zero. This is namely the case when the M052 software writes its release date there. If the time is nonzero, however, it is assumed that a system clock is updating these memory cells. In that case, the four memory cells 000Ch to 000Fh are used as the source for the system time. In all other cases, there is no system time available for the compiled BASIC program.
      Caution! An even number of seconds is always read from the memory cells 000Ch to 000Fh, since the format of the DOS timestamp does not allow odd numbers of seconds.
  • The JOYST function queries the joystick module (M008 or M021) directly, i.e., no special joystick driver needs to be loaded. For this, the compiled program initializes the corresponding PIO in the joystick module at startup, but only if the BASIC program also contains a JOYST call. The joystick PIO is programmed to the same operating mode used by the joystick driver in CAOS 4.5. As a result, that driver is not affected.
  • VDIP is supported via module M052. On the OPEN statement, the compiled program first checks the CAOS version. If it is lower than 4.8, an M052 module is searched for, activated, initialized and used. Any USB keyboard connected to the module will therefore stop working. If the CAOS version is 4.8 or higher, the program checks whether the driver active in CAOS is a USB driver. If so, it is used. If not, the program searches the CAOS driver table for a USB driver and activates the first one found. The driver is then switched to USER mode, so that the compiled program can access the M052 module directly. On the CLOSE statement, it is then switched back to CAOS mode. Any USB keyboard that is connected should therefore continue to work.
  • The constant for the target system is: TARGET_KC85

KC85/4..5 with support for both video memory banks

This target system is specially tailored to the hardware of the KC85/4 and KC85/5, and thus makes it possible to use both video memory banks. In addition, the graphics routines have been optimized for the specific hardware, so that they are somewhat faster than with the general KC85/2..5 target system described further above.

The KC85/4..5 target system provides the two SCREENs 0 and 1, which represent the two video memory banks (IRM banks) 0 and 1. For each video memory bank, i.e. for each SCREEN, the cursor is managed separately. You can therefore switch between the two SCREENs and output text on both video memory banks, without this having any effect on the other video memory bank.

Properties of the target system in detail:
  • SCREEN 0 allows output of text and graphics using IRM bank 0.
  • SCREEN 1 allows output of text and graphics using IRM bank 1.
  • A separate CAOS window is used for each SCREEN, so that each SCREEN also has its own cursor management.
  • Everything else is as for the target system KC85/2..5, HC900
  • The constant for the target system is: TARGET_KC85_4
  • This target system is derived from the target system KC85/2..5, HC900, i.e., the function IS_TARGET also returns TRUE for TARGET_KC85.

KC85/5 with CAOS >= 4.8

With operating system version CAOS 4.8, system functions were introduced that let application programs access a USB storage device and, in doing so, also take advantage of that storage medium's features, such as subdirectories and byte-accurate file sizes. Furthermore, the DEVICE interface introduced with CAOS 4.6 was further developed, so that application programs can now benefit from it more effectively. To support these new capabilities, there is the target system KC85/5 with CAOS >= 4.8. It is derived from the target system KC85/4..5 with support for both video memory banks and therefore has the same properties as that one, except for the following two points:

  • VDIP driver (access to USB storage)

    The generated program code no longer contains its own VDIP driver; instead, it calls the new driver-specific functions of the CAOS USB driver. For the BASIC programmer, these behave exactly the same as the otherwise used custom VDIP driver. However, the compiled program is smaller, and the M052 module remains entirely under the management of the operating system. Other USB devices connected to the M052, such as a keyboard, are therefore not affected.

  • DISK driver (access to drives in D004/D008)

    If you have the D004 or D008 floppy disk expansion connected and the floppy disk expansion program DEP is running on it, you can access the floppy or hard disk drives from CAOS. In that case, CAOS 4.8 automatically sets up a DISK driver that provides access for application programs. The target system makes use of this. If you open a file in the BASIC program on the devices A: through P:, this goes via the CAOS DISK driver. There are a few things to note here:
    • The floppy or hard disks use a CP/M-compatible file system. As a result, files always have a byte length that is a multiple of 128 (the block size). In text mode, byte 1Ah is used as the end-of-file marker, i.e., when closing a file that was opened for writing, byte 1Ah is automatically appended, and when reading, this byte marks the end of the file. In binary mode, on the other hand, reading continues up to the last physically present byte.
    • Two files cannot be open at the same time via the DISK driver.
    • The CAOS DISK driver does not support appending to an existing file, i.e., for the BASIC statement OPEN, the mode APPEND is not possible.
    • An empty file cannot be opened; only one that is at least one block (128 bytes) in size.
    • When writing a file, at least two blocks are created (one when opening and one when closing the file), i.e., the file is always at least 256 bytes in size.
    • When writing, the file is only physically opened once the first block is written. As a result, any errors that would normally occur on the OPEN statement only occur on the statements used for output, or even only on CLOSE.
    • In the event of an error, the CAOS system functions themselves output an error message to the screen. The calling program is only told, in general terms, that an error has occurred. For this reason, the BASIC error variables usually only contain a general error as well.

If, for this target system, you have activated both the DISK and the VDIP driver in the compiler options, and you open a file without specifying a drive letter (in BASIC terminology, a device name), the DISK driver is used, i.e., the file is opened on the floppy or hard disk drive that is currently selected.

A program compiled for this target system will also run on a KC85/4 or KC85/5 with a CAOS version lower than 4.8. However, attempting to open a file results in the error message Device not found.

The constant for the target system is: TARGET_KC85_CAOS48. The function IS_TARGET also returns TRUE for TARGET_KC85 and TARGET_KC85_4, since this target system is derived from them.

SCCH (AC1-2010, AC1-SCCH, LLC2)

If this target system is selected, program code is generated for an AC1 or LLC2 with an SCCH monitor program. The program code will also run on an AC1 with monitor program 3.1, provided printer output, the LOCATE statement and the JOYST function are not used.
  • A single-character application name is supported, i.e., if the name field contains only one character, a corresponding command frame is generated, and the compiled program can be invoked using that character.
  • The graphics statements are not available.
  • The CURSOR statement has no effect.
  • The PAUSE statement is calibrated to the standard clock frequency of the AC1 (2 MHz). On an LLC2, due to the higher clock frequency, the wait time is correspondingly shorter.
  • The DATETIME$ function requires a GIDE connected at I/O base address 80h.
  • The JOYST function supports a joystick and, for this purpose, calls the system function at address 0EB4h.
  • A VDIP module is supported at I/O base addresses DCh and FCh, i.e., an attempt is first made to initialize the VDIP module at base address DCh. If that fails, base address FCh is tried next.
  • The constant for the target system is: TARGET_SCCH

Z1013

  • In SCREEN 0, full graphics with 64x64 pixels are simulated and can be addressed with the graphics statements.
  • The DATETIME$ function requires either a real-time clock module at I/O base address 70H or a GIDE at I/O base address 80h.
  • The JOYST function calls the jump table, but only if there is a jump instruction (byte C3h) at address FFBBh (entry point for the joystick query). This is a safeguard so that the compiled program does not crash if the jump table has not been initialized.
  • Printer output is performed via the jump table, but only if there is an absolute jump instruction (byte C3h) at address FFE8h (routine for outputting the character in register A).
  • The option CTRL-C always aborts the program slows down the program considerably. The reason is the slow INKEY routine of the Z1013 monitor program, which is called regularly to check for abort.
  • A VDIP module is supported at I/O base addresses DCh and FCh, i.e., an attempt is first made to initialize the VDIP module at base address DCh. If that fails, base address FCh is tried next.
  • The constant for the target system is: TARGET_Z1013

Z1013 with support for the 64x16 screen format

This target system is an extension of the Z1013 target system. The only difference is that there is an additional SCREEN 1, which provides the Peters board's 64x16-character mode. Since the Z1013 monitor programs do not support this screen format, screen output in SCREEN 1 is performed via a custom screen driver included in the compiled program. This supports the same control codes and also uses the same system cells as the original routine in the monitor program.

Properties of the target system in detail:
  • SCREEN 1 is a pure text screen with 64x16 characters.
  • Everything else is the same as for the target system Z1013.
  • The constant for the target system is: TARGET_Z1013_64X16
  • This target system is derived from the target system Z1013, i.e., the function IS_TARGET also returns TRUE for TARGET_Z1013.

Z1013 with KRT graphics

This target system is likewise an extension of the Z1013 target system, in which there is an additional SCREEN 1 that supports the full graphics extension described in Kleinstrechnertips 11 and Funkamateur 7/1991. In return, the simulated full graphics with 64x64 pixels are not available in SCREEN 0.
  • SCREEN 0 is a pure text screen. Full graphics are not simulated, i.e., the graphics statements cannot be used here.
  • The full graphics with 256x256 pixels are available in SCREEN 1, i.e., the graphics statements can be used here. Text output, however, is not possible (except with the LABEL statement).
  • Everything else is the same as for the target system Z1013.
  • The constant for the target system is: TARGET_Z1013_KRT
  • This target system is derived from the target system Z1013, i.e., the function IS_TARGET also returns TRUE for TARGET_Z1013.

Z1013 with ZX graphics

This target system is also an extension of the Z1013 target system, in which there is an additional SCREEN 1 that supports the ZX Spectrum-compatible black-and-white full graphics described in practic 2/1988. In return, the simulated full graphics with 64x64 pixels are not available in SCREEN 0.
  • SCREEN 0 is a pure text screen. Full graphics are not simulated, i.e., the graphics statements cannot be used here.
  • The ZX full graphics with 256x192 pixels are available in SCREEN 1, i.e., the graphics statements can be used here. Text output, however, is not possible (except with the LABEL statement).
  • Since this graphics extension uses white as the background color, a set pixel is black. Consequently, the POINT function also returns, for a set pixel, the numeric value for the constant BLACK.
  • Everything else is the same as for the target system Z1013.
  • The constant for the target system is: TARGET_Z1013_ZX
  • This target system is derived from the target system Z1013, i.e., the function IS_TARGET also returns TRUE for TARGET_Z1013.
