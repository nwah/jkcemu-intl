1. File Formats for Disk Image Files

The file formats for disk image files supported by JKCEMU can be found here.

2. File Formats for Memory Image Files

JKCEMU supports various file formats for memory image files. These are used to save an area of the working memory of the emulated system into a file and, conversely, to load data from a file into the working memory. Some file formats are only suitable for certain kinds of data, e.g. for BASIC programs. Most file formats, however, are suitable for storing any binary data. In principle, you can use any of these file formats to store the programs and data of any emulated system. However, it is recommended to only ever save programs in one of the formats that are customary for the emulated system.

2.1. Headersave Format

The Headersave format is essentially the standard format on the Z1013. It is a good idea to also use this format as the standard format for AC1 data within the emulator environment.

In terms of content, the Headersave file format matches the Headersave cassette recording format of the Z1013. It contains a 32-byte header block, followed by the data area, which in turn represents a 1:1 image of part of the working memory. The usual file extension is *.z80.

The header block has the following structure:
Offset Length Field Meaning
0 2 bytes Start address Start address in working memory,
The data area of the file following the header block is loaded into the memory area starting at this address. It is usually also possible to specify a different address when loading. In that case, the start address given in the header block is ignored.
2 2 bytes End address End address in working memory,
(End address - start address + 1) bytes are loaded.
4 2 bytes Launch address The launch address is only relevant if the file contains an executable machine code program (file type "C"). The program is started with a jump instruction to this address.
12 1 byte File type The file type is specified with a letter. The most important types are:
A: Assembler source code
B: BASIC program
b: Mini/Tiny BASIC program
C: Machine code program, self-starting
M: Machine code program
13 3 bytes Headersave identifier This contains three bytes with the hexadecimal value D3.
16 16 bytes File name This is a label of up to 16 characters that serves as the file name when saving to magnetic tape. If the label is shorter than 16 characters, it is padded with spaces.
Since with the emulator the file resides in the file system of the computer and thus already has a name, this field only has the meaning of an additional label. This label does not have to match the name in the file system.

Headersave files are little-endian encoded, i.e., the low-order byte comes before the high-order byte. This also applies to the address fields in the header block.

2.1.1. Headersave Cassette Recording Format

The two original Z1013 monitor programs (2.02 and A.2) save programs and data by writing an area of the working memory to the storage medium (magnetic tape). In doing so, no management information is stored, i.e., the user has to remember the start and end address of the memory area, and, for a machine code program, also the launch address, separately.

This simple approach is not very convenient and was therefore already extended, in the Tiny BASIC interpreter printed as a hex listing in the Z1013 manual, with a 32-byte header block containing management information. This method was later further developed by dedicated Z1013 users into the so-called Headersave format, which established itself as a quasi-standard. However, the Headersave format was never implemented at the factory in any Z1013. Nevertheless, it is still possible to load a Headersave file from cassette with the original monitor programs, by starting the load only after the acoustically clearly distinguishable header block.

The header block in the recording format of the Tiny BASIC interpreter is compatible with the Headersave format. Only the launch address and the Headersave identifier are missing.

2.2. KCB Format

The KCB format is identical to the KCC format (see further below). The different file extension only indicates that the file contains a KC-BASIC program, even though the file format is that of a KC system file and not that of a KC-BASIC file. This packing of a BASIC program into a system file is usually done to make the BASIC program self-starting. For this purpose, the file additionally contains a small machine code routine, which the launch address in the header data points to.

JKCEMU supports the KCB format in that it loads the BASIC program and relocates it for the RAM or ROM BASIC, as applicable. The machine code and any other data contained in the file are ignored. If, on the other hand, you want to load the file completely, i.e. not just the BASIC program, you must treat the file as a KCC file, i.e. simply change the format in the dialog with the loading options. However, in that case the BASIC program will no longer be relocated.

2.3. KCC Format

The KCC format is used by several KC emulators and has its origin in the cassette recording format of the KC computers (KC85/1-4, KC87, Z9001). The file format contains a header block, followed by the data area, which in turn represents a 1:1 image of part of the working memory. The usual file extension is *.kcc.

The header block has the following structure:
Offset Length Field Meaning
0 8 bytes File name This is a label of up to 8 characters that serves as the file name when saving to magnetic tape.

Caution! If the name is shorter than 8 characters, zero bytes are entered for KC85/1, KC87 and Z9001, whereas spaces are entered for HC900 and KC85/2..5.

Since with the emulator the file resides in the file system of the computer, it already has a name. This name does not have to match the name stored in the file header.
8 3 bytes File type This is a file type of up to 3 characters. The most important types are:
ASM: Assembler source code
COM: Machine code program
DUM: Memory dump
KCB: KC-BASIC program saved as a machine code program
KCC: CAOS machine code program
TXT: Text file

Caution! On HC900 and KC85/2..5, this field is defined as a file type (see KC85/3 System Manual, page 88), but a file type is not taken into account when saving and loading via cassette. Instead, file name and file type together are used as an 11 character-long file label (see KC85/3 System Manual, page 32), which, if it is shorter than 11 characters, is padded with spaces. For this reason JKCEMU also uses an 11 character-long label for HC900 and KC85/2..5.
16 1 byte Number of following addresses This field specifies the number of following addresses (start, end and, if applicable, launch address). If a number greater than 3 is present here, the file still only contains 3 addresses. However, an HC900 or KC85/2..5 will then not convert the launch address with an address offset when loading the file.
17 2 bytes Start address Start address in emulated working memory
19 2 bytes End address End address in emulated working memory

Caution! On HC900 and KC85/2..5, the end address + 1 is entered (see KC85/3 System Manual, page 88).
21 2 bytes Launch address This address is used to start the machine code program contained in the file.
The launch address is only valid if the field Number of following addresses has a value of three or greater.

KCC files are little-endian encoded, i.e., the low-order byte comes before the high-order byte. This also applies to the address fields in the header block.

Caution! The second address entered in the file header is, for KC85/1, KC87 and Z9001, the actual end address, and for HC900 and KC85/2..5 the end address + 1. However, this does not seem to be implemented that way everywhere. To ensure that the last byte is never lost, JKCEMU handles the KCC format as follows:
  1. When saving, the end address is entered into the file header according to the rule above. The KC header thus matches the official documentation.
  2. When loading, data is loaded up to and including the address entered in the header data, i.e. possibly one byte too many.
This ensures that never one byte too few is loaded, regardless of whether a third-party program wants to load a KCC file created by JKCEMU, or vice versa.

2.3.1. KCM Format

The KCM format is identical to the KCC format. The difference in the file extension is meant to indicate that the file contains machine code, but not an executable program.

2.3.2. JTC Format

In its expansion stage with the extended operating system EMR-ES 1988, the Jugend+Technik computer uses the cassette recording format of the KC computers. For this reason, the KCC file format is also used by JTCEMU, the Ju+Te computer emulator. However, to make it clear that such a file contains not a KC program but a Ju+Te computer program, the format is called the JTC format in JTCEMU (file extension is *.jtc).

Caution! Contrary to the KC85/3 documentation, the Ju+Te computer enters the actual end address into the file header. For this reason the JTCEMU emulator does so as well.

2.3.3. Deviating KCB, KCC and KCM Files

Occasionally, files can be found that deviate from the format described above. These deviating files are usually a conversion of cassette recordings. On cassette, KC files are recorded in blocks, where each block contains a block number and a checksum byte. Deviating KCB, KCC and KCM files contain the block numbers, or the block numbers and checksum bytes. JKCEMU recognizes such files and marks them as file type B (contains block numbers) or file type B+P (contains block numbers and checksum bytes). Such files can be loaded into the emulator, but not saved.

2.4. KC-BASIC Program Files

A KC-BASIC program file usually has the file extension *.sss and contains, at the beginning, two bytes that specify the length of the BASIC program. The actual program follows starting at the third byte. After that comes a byte with the value 3, followed by filler bytes, until the file length is a multiple of 128 bytes.

Some KC-BASIC program files have an 11-byte file header, which begins with a BASIC program file identifier (three times D3 or three times D6) and, after that, contains an 8-character-long name.

JKCEMU can load both kinds of KC-BASIC program files. When saving, however, only the form without header data is supported.

KC-BASIC program files are little-endian encoded, i.e., the low-order byte comes before the high-order byte. This also applies to the length field at the beginning of the file.

2.4.1. Deviating KC-BASIC Program Files

As with KCB, KCC and KCM files, there are also deviating formats for KC-BASIC program files. JKCEMU recognizes such files and marks them as file type K (contains header), file type K+B (contains header and block numbers), or file type K+B+P (contains header, block numbers and checksum bytes). The header contains the three KC-BASIC type bytes followed by the eight characters for the name. These deviating files can be loaded into the emulator, but not saved.

2.5. KC-TAP Format

The KC-TAP format was defined by Arne Fitzenreiter and is used by many KC emulators. It is derived from the cassette recording format of the KC computers not only in content but also in its management structure, since besides the payload bytes it also contains block numbers.

The KC-TAP format begins with a 16-byte identifier, followed by 129-byte blocks. Each block begins with a block number followed by 128 payload bytes. The first block is usually the header block and provides information about the type and the length of the file.

The file has the following structure:
Offset Length Meaning
0 16 bytes KC-TAP identifier with the hexadecimal byte sequence:
C3 4B 43 2D 54 41 50 45 20 62 79 20 41 46 2E 20

Written as a C string:
"\xC3KC-TAPE by AF. "
16 129 bytes Header block
145 129 bytes 2nd block
... ... ...
16 + ((n - 1) * 129) 129 bytes Block n
The last block often has block number 255 (hexadecimal: FF).

If you leave out the KC-TAP identifier and the block numbers and simply chain together the payload data of the individual blocks, you get either the KCC or the KC-BASIC program file format, depending on what the KC-TAP file contains.

Caution! Regarding the end address entered in the header block of the KC-TAP format, the same applies as for the KCC format (see here).

Note: KC-TAP files are also supported as tape files and can therefore also be loaded into the emulator with the function Read audio data from a sound or tape file. This is, by the way, the only way to load a KC-TAP file that contains a KC-BASIC program in ASCII format or a KC-BASIC data field in such a way that the BASIC interpreter can actually make use of it.

2.5.1. Multi-KC-TAP Files

Several KC-TAP files can be chained together into a single file, which logically means several consecutive cassette recordings. Such files are called Multi-KC-TAP files.

Multi-KC-TAP files are suitable for programs that consist of several files. In most cases these are game programs. The first file, i.e. the first cassette recording, often contains only a small program which displays a start screen and then reads in the remaining files, i.e. the subsequent cassette recordings, and then starts the actual program.

JKCEMU supports Multi-KC-TAP files as follows:
  1. When loading into working memory, only the first partial file is loaded and started, if applicable.
  2. JKCEMU detects the presence of further partial files and asks the user whether these should be fed to the audio system, so that they can be read in through it.
Independently of this, Multi-KC-TAP files can also be read in fully through the audio functions and converted into a sound file with the File Converter.

2.6. BASIC Program Files

A BASIC program file contains a BASIC program exactly as it is present in working memory. The first byte in the file is the first byte of the actual BASIC program. The file extension is *.bas (exception for AC1-BASIC6: *.abc).

2.7. RBASIC Program Files

The A5105 (BIC, ALBA-PC) uses this file format to store BASIC programs on floppy disk. The first byte in the file has the value 0FFh. After that follows the RBASIC program exactly as it is found in the working memory of the A5105 starting at address 8001h. After that, i.e. following the three trailing zero bytes of the BASIC program, follows a byte 1Ah. The usual file extension is *.bas.

2.8. Intel HEX Format

In an Intel HEX file, the binary data is stored as hexadecimal numbers in textual form, i.e., the Intel HEX file is a pure ASCII file. The data is grouped into segments, so-called records, where usually each segment forms its own line of text. The structure of a record is:
Offset Length Field Meaning
0 1 character Start marker This contains a colon. All characters between the previous record and the start marker are ignored. This usually concerns a line break.
1 2 characters Number of data bytes The number of data bytes is given in hexadecimal.
3 4 characters Start address of the record The address is given in hexadecimal.
7 2 characters Record type 00: Data record
01: End-of-file record
Other record types are, depending on the type, either ignored or cause loading to abort.
9 n characters Data of the record Each pair of characters hexadecimally encodes one data byte, i.e., the record contains n / 2 data bytes.
9 + n 2 characters Checksum The checksum is the lower 8 bits of the result of zero minus the sum of the individual bytes, where two hexadecimal characters each form one byte.

The end-of-file record usually looks like this: :00000001FF

2.9. Plain Memory Image Files

A plain memory image file contains a pure image of a part of the emulator's working memory. It contains no header data, i.e., the start address and, if applicable, the launch address must be remembered separately. The usual file extension is *.bin.

2.10. CP/M Program Files

CP/M program files have the extension *.com and contain the pure memory image of a CP/M-compatible program. The file format is thus the same as for BIN files, only the extension is different. CP/M-compatible operating systems load COM files to address 0100h and then start the program there. For this reason JKCEMU also assumes the start address 0100h for COM files and loads them there by default.

3. File Formats for Sound Files

The following sound file types are supported for both reading and writing:
  • AIFF (*.aif; *.aiff)
  • AU (*.au)
  • WAVE (*.wav)

In a sound file, the audio data is present in a certain format or a certain encoding. JKCEMU only supports uncompressed PCM audio data (Pulse Code Modulation), which is usually stored with 8- or 16-bit resolution. PCM audio data as floating-point numbers, A-law or μ-law encoding, or compressed audio data is not supported. However, it is possible to read and write GZip-compressed sound files. For this, the file extension .gz must be appended, or must be appended when writing.

4. File Formats for Tape Files

Tape files contain the data of a digital magnetic tape recording (usually from a cassette). Since magnetic tape recordings are originally loaded into the computer via the cassette interface, tape files must be loaded into JKCEMU via the emulated cassette interface. For this, the function Read audio data from a sound or tape file is used.

Tape files differ from sound files in that they contain either the audio data with only one bit of resolution, or even only the actual data bytes. In the second case, information may also be included on how the data bytes are to be converted into audio data. Tape files are usually significantly smaller than sound files.

3.1 CDT Format

CDT stands for CPC Digital Tape. The format is identical to the TZX format. The different name and the different file extension are only meant to show that a CDT file contains programs or data for CPC computers or their compatibles, such as the KC compact.

3.2 CSW Format

CSW stands for Compressed Square Wave and was developed specifically for storing digital cassette recordings. The format stores the audio data with one bit of resolution.

JKCEMU supports reading and writing CSW files, both in the old CSW1 format and in the CSW2 format. If you specify the extension .csw when saving a file, it is saved in the CSW2 format. If needed, you can also produce the old CSW1 format. To do this, you must specify the extension .csw1 and, after saving, rename the file to .csw.

3.3 TZX Format

The TZX format was developed to store magnetic tape recordings for the ZX Spectrum. Besides the ZX Spectrum standard recording method, the format can also represent turbo loaders and other custom recording methods. This requirement, combined with the principle of storing, wherever possible, only the actual data bytes rather than audio data, makes the TZX format quite complicated, however.

A TZX file consists of individual blocks. There are various kinds of blocks to represent metadata, control information and, of course, the data to be stored in the various recording methods.

JKCEMU supports TZX files, but with a few restrictions:
  • JKCEMU cannot process all block types (block IDs). If a TZX file contains an unsupported block ID, the file cannot be loaded into the emulator.
  • When creating a TZX file (Record audio data and save to file or converting a CSW file into a TZX file in the File Converter), the audio data is stored in a block with ID 15h (Direct Recording Block). According to the developers of the TZX format, this block ID should only be used when no other block ID is suitable. The purpose of the TZX format is, after all, to store the payload data directly wherever possible, rather than the audio data. Since this is not readily possible in this case, however, JKCEMU uses block ID 15h.

3.4 TAP Format

TAP stands for Tape. However, there is not just one TAP format, but many. Of the many, JKCEMU supports the KC-TAP and the ZX-TAP format. Both formats are supported as a tape file only for reading, i.e., they can be read in via the emulated cassette interface, but not saved. In addition, the KC-TAP format is also supported as a memory image file, and in that case fully, i.e. for both reading and writing. This means that areas of working memory can be saved directly to a KC-TAP file and loaded from there directly back into working memory. This is done via the emulator functions provided for this purpose (see Loading, Starting and Saving Programs and Files) and not via the emulated cassette interface.
